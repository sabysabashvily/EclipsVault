Accepted decisions
RefAgreed behavior
Q1Sensitive changes

Email, password, authenticator, recovery-code and passkey changes require fresh proof from existing credentials. Display-name/avatar edits and signing out everywhere do not require this extra proof.

Q2Authenticator flow

Keep reset → sign out → Legacy enrollment when sign-in requires local TOTP. Retire the old TOTP and recovery codes atomically; invalidate sessions and affected pending proofs. No in-place authenticator replacement in Profile.

Q3Password-change session

Keep the verified browser signed in with a genuinely fresh session and new session ID. Invalidate its previous cookie and other sessions; remove future-dated authentication timestamps.

Q4Recovery-code display

Keep ten codes, Print and Done. Deliver plaintext once into current page memory; clear it on departure or session loss. No cookie, browser storage or URL retention. Refresh/direct visits return to Profile; a lost response requires deliberate regeneration.

Q5Shared repair boundary

Repair the shared backend and affected Legacy callers narrowly; leave sign-in/enrollment pages for Area 8. Profile database mutations and semantic audit events commit together. Field-specific updates and concurrency controls prevent cosmetic writes from restoring stale credentials or security state.

Q6Accepted account proof

Accept current password + TOTP, current password + an unused recovery code, or an already registered passkey with user verification. Enforce the session account server-side. Password changes additionally require the current password, including when a passkey supplies verification.

Q7One operation

A server-held authorization covers one operation with frozen intended data, bound to account, session and original credential generation. It expires five minutes after verification and is consumed once. Changed data requires new verification; no general unlocked Profile period.

Q8Durable credential generation

Advance a database credential generation atomically with the change, authorization consumption and audit. Carry the original generation through pending proof and issuance; never upgrade stale proof by rereading the latest value. Refuse old generation-less cookies/proofs and retire older application nodes at rollout.

Q9Completed-change invalidation

Every completed password, active email, recovery-set or passkey add/remove change invalidates prior sessions and retains a fresh current session. Authenticator reset ends all sessions, including current. Cosmetic edits and merely starting a change do not end sessions.

Q10Email ownership

Require both account verification and new-mailbox ownership before activation. Keep the old address active while pending or delivery fails. Without configured, enabled SMTP, email is read-only with an explanation. Confirmation secrets stay out of logs, audit and recorded notification bodies.

Q11Throttling and replay

Reuse configured shared IP and account limits across verification methods: defaults 11 requests/120 seconds and five failures/15-minute lockout. Make failure counts, TOTP replay and recovery consumption atomic. Reset failures only after the entire intended proof succeeds. Browser cancellation is not a wrong credential; sign-out remains unmetered.

Q12SSO without local proof

Keep sensitive changes unavailable with an explanation when no usable local proof exists. Add no fresh-IdP verification protocol in Area 3. An SSO session alone is insufficient; do not imply an existing administrator password-reset feature.

Q13Mailbox confirmation

Use one pending target and a single-use mailbox code valid for 15 minutes, entered on the original signed-in Profile page. Account authorization must still be within five minutes at activation or be repeated for that exact target. Consume it at activation. Resend/replacement invalidates the old code; cancellation is available.

Q14Mailbox attempt limits

Five wrong attempts invalidate the pending code. Limit sends/resends to one per minute and six per hour per account, with shared source-IP protection. Mailbox mistakes do not lock ordinary sign-in; delivery failure leaves active email unchanged.

Q15Passkey ceremony state

Enforce a 120-second server deadline, purpose/session binding and account/generation binding where known. Consume challenges atomically once. Starting a new attempt replaces the prior attempt for that session and purpose.

Q16Last passkey

Require proof of a different local method that remains usable after deletion. The removed key, an unproved password hash or an SSO session cannot qualify. A spent recovery code cannot count as fallback; recheck surviving recovery capability in the deletion transaction, serialized with redemption.

Q17Reset scope and guards

Retire TOTP, its replay marker and recovery codes; retain unrelated passkeys and SSO. Reenroll when local TOTP is required at sign-in. Server-side guards refuse reset without enrollment and recovery generation without TOTP; return availability and reasons.

Q18Committed and uncertain outcomes

Keep a committed change and its invalidation even if cookie renewal or response delivery fails. Never automatically retry the mutation. Distinguish a known commit requiring sign-in from an unknown outcome; check state/sign-in before deliberate retry. Metadata failure is best-effort; lost recovery plaintext is not retained.

Q19Explicit session revocation

Use atomic session-store revocation versions instead of timestamps, with memory/Redis parity and per-device tombstones. Capture the version before loading the authentication snapshot and carry it through issuance. Preserve it on ordinary renewal/step-up. Refuse missing state; initialize new state atomically with a non-repeating value, never from a cookie. Migrate every account-wide revocation caller.

Q20Truthful sign-out

Clear the local cookie regardless of revocation/audit outcome. Revoke first, then audit confirmed results. Return revoked_unrecorded for confirmed revocation with failed audit, or sign_out_incomplete for uncertain/incomplete revocation. Preserve the warning through Legacy sign-in.

Q21Security notifications

After every completed sensitive change, attempt notification to the existing trusted address; capture the old address before email activation. Delivery is best-effort and secret-free, and cannot undo the committed change. Ownership-code delivery remains separate.

Q22Discoverable passkey boundary

Preserve username-less passkey sign-in. Capture and fence account generation when the credential identifies its owner, before verification. An unchanged registered key may answer an unexpired anonymous challenge begun before another credential change; removed keys and stale named-account proofs remain invalid.

Q23Email comparison

Trim and compare email identities case-insensitively while preserving spelling for display/delivery. Enforce matching uniqueness in both databases, including disabled accounts. Fail migration on canonical/alias collisions for explicit resolution; never merge/select an owner. Activation races return a generic conflict. No dot/plus alias folding.

Q24Account lookup

Give SSO an email-only lookup. Combined username/email callers reject matches to different account IDs. Enforce Web username rules in Core, and explicitly resolve preexisting cross-account aliases. Keep username case policy and the OIDC protocol unchanged.

Q25Prepared typed operations

Prepare frozen intended data on the server, use shared verification and typed final-action endpoints. Operation IDs alone confer no authority. Bound preparation lifetime, active state, admission and hashing concurrency before expensive work. Use safe response allowlists, stable Problem Details and HTTP contract tests; wrong proof stays on Profile, while 401 means an unusable session.

Q26Profile controls

Keep the existing cards, with separate display-name Save and email-change controls. Use an accessible shared verification dialog, destructive ConfirmationDialog first without nesting, and StatusLine. Cancel/Escape restore focus and clear sensitive input; prevent duplicate submissions and refresh shared account/antiforgery state after renewal.

Q27Routes and compatibility

Keep /Profile/Avatar as a shared session-only binary route with no-store, intentional cross-account avatar reads and existing upload protections. Preserve case-insensitive Profile page URLs. Move breach preview to the UI API for Profile and Legacy Create user; retire unsafe Legacy Profile write handlers at cutover.

Q28Named presentation fixes

Replace “Change it periodically” with compromise-based password advice. Show passkey creation dates explicitly in UTC. Preserve other appearance/text except accepted security flows, including CSP-safe meter, show/hide, length/confirmation, unchanged-password refusal and breach checks.

Q29SSO and verification coverage

Reuse the existing fixture beginning after IdP assertion for the real callback, account matching, attribution and proof policy. Full external IdP/browser protocol coverage remains Area 8; do not claim that the fixture validates IdP tokens. Retain the full real-failure, concurrency and browser test plan.

Q30Outage-only local clearing

Provide an exact-route terminal anonymous GET-token/antiforgery-protected POST outside the UI API and before store-backed middleware. It only clears the configured local authentication cookie, reads no account identity, performs no server revocation and never enters protected routes. Preserve sign_out_incomplete; test allowlisting, methods, CSRF and cookie chunks.

Q31Redis recovery gate

Before traffic resumes after recovery that may have lost revocation writes, rotate a session-store incarnation outside the restored Redis keyspace across all nodes. Invalidate old sessions and fence pending session-bound proofs. Document and test the gate; the guarantee requires coordinated recovery and cannot automatically detect undisclosed rollback.
