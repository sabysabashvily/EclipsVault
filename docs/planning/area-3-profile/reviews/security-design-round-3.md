1. **Reset does not guarantee enrollment at the next sign-in.** Reset clears TOTP and recovery codes but retains passkeys ([ProfileService.cs:155](../../../../EclipsVault.Core/Application/Profile/ProfileService.cs:155)). Passkey and trusted-IdP sign-in issue full sessions without checking TOTP enrollment ([AccountController.cs:273](../../../../EclipsVault.Web/Controllers/AccountController.cs:273), [434](../../../../EclipsVault.Web/Controllers/AccountController.cs:434)). Conversely, an IdP requiring local MFA also enters enrollment when TOTP is disabled ([441](../../../../EclipsVault.Web/Controllers/AccountController.cs:441)). Therefore “reenroll only during password sign-in” is inaccurate unless deliberately changing that IdP branch. Recommend wording: enrollment occurs when sign-in requires local TOTP; retained passkeys and trusted IdP MFA remain usable.

2. **Neither proposed recovery/deletion guard exists.** Recovery generation checks account existence, not `TotpEnabled`, while redemption requires TOTP enabled ([MfaRecoveryService.cs:39](../../../../EclipsVault.Core/Application/Mfa/MfaRecoveryService.cs:39), [VaultAuthenticationService.cs:115](../../../../EclipsVault.Core/Application/Authentication/VaultAuthenticationService.cs:115)). A passkey user after reset can therefore generate currently unusable codes. Passkey removal checks ownership only, permitting deletion of the last credential without alternate proof ([PasskeyService.cs:258](../../../../EclipsVault.Infrastructure/Security/WebAuthn/PasskeyService.cs:258)). Recommend server enforcement of both guards. A stored password hash, remaining passkey count, or active SSO session does not establish usable alternate proof. Existing assertion results also omit the proving credential ID, which matters when excluding the credential being removed ([PasskeyDtos.cs:23](../../../../EclipsVault.Core/Application/Passkeys/PasskeyDtos.cs:23)).

3. **SMTP can deliver verification without recording its secret, but the ordinary notification workflow cannot.** `SmtpEmailSender` sends without persisting the body; `NotificationService` stores the entire body and raw delivery-error message, and returns “recorded” even for failed/suppressed delivery ([SmtpEmailSender.cs:19](../../../../EclipsVault.Infrastructure/Notifications/SmtpEmailSender.cs:19), [NotificationService.cs:123](../../../../EclipsVault.Core/Application/Notifications/NotificationService.cs:123)). The Log sender itself logs recipient and subject, not body ([LoggingEmailSender.cs:19](../../../../EclipsVault.Infrastructure/Notifications/LoggingEmailSender.cs:19)).

   Recommend a narrow verification-delivery seam enforcing enabled SMTP and excluding redeemable material from history, audit and diagnostics. Calling `IEmailSender` directly otherwise bypasses the existing enabled check. SMTP acceptance remains delivery evidence, never ownership proof.

   A 15-minute mailbox-code lifetime can coexist with five-minute account proof: at minute eight, require fresh account verification and consume that unexpired authorization at activation. Do not extend the old proof. Define which stage consumes the one-operation authorization; consuming it when requesting mail cannot also authorize activation. Mailbox-code guessing/resend limits remain unspecified.

4. **Email uniqueness has provider-dependent casing and no duplicate-conflict mapping.** Profile trims email without normalizing case; lookup uses database equality, and uniqueness indexes the original column ([ProfileService.cs:68](../../../../EclipsVault.Core/Application/Profile/ProfileService.cs:68), [UserRepository.cs:20](../../../../EclipsVault.Infrastructure/Persistence/Repositories/UserRepository.cs:20), [UserConfiguration.cs:19](../../../../EclipsVault.Infrastructure/Persistence/Configurations/UserConfiguration.cs:19)). PostgreSQL uses ordinary `varchar`, not `citext`; SQL Server inherits its database collation ([InitialPostgres.cs:183](../../../../EclipsVault.Migrations.Postgres/Migrations/20260716154841_InitialPostgres.cs:183)). Thus case variants can coexist under ordinary case-sensitive PostgreSQL settings while conflicting under case-insensitive SQL Server settings. No live collation was inspected.

   A duplicate currently escapes as an unhandled database exception: UI API handling produces `500 internal_error`, not a domain conflict ([GlobalExceptionMiddleware.cs:81](../../../../EclipsVault.Web/Middleware/GlobalExceptionMiddleware.cs:81)). Settle consistent identity comparison, recheck uniqueness at activation, and map the constraint race to a generic conflict without disclosing another account.

5. **Atomic semantic auditing is feasible; generic `User → ProfileUpdated` rules would be wrong.** The interceptor supports multiple rows and caller-owned transactions, but currently describes entities individually ([AuditSaveChangesInterceptor.cs:146](../../../../EclipsVault.Infrastructure/Persistence/Interceptors/AuditSaveChangesInterceptor.cs:146), [AuditChain.cs:48](../../../../EclipsVault.Infrastructure/Persistence/AuditChain.cs:48)). Concrete traps:

   - Sign-in updates TOTP replay/lockout fields; step-up updates `LastTotpStep`. Neither is a Profile edit ([VaultAuthenticationService.cs:104](../../../../EclipsVault.Core/Application/Authentication/VaultAuthenticationService.cs:104), [StepUpService.cs:47](../../../../EclipsVault.Core/Application/StepUp/StepUpService.cs:47)).
   - Admin role, enabled-state and TOTP changes already emit distinct semantic events ([UserAdminService.cs:182](../../../../EclipsVault.Core/Application/Users/UserAdminService.cs:182)).
   - Reset/recovery replacement changes several entities; per-row rules would multiply one operation into misleading events. Broad `Users.Update` also marks unrelated fields modified ([UserRepository.cs:45](../../../../EclipsVault.Infrastructure/Persistence/Repositories/UserRepository.cs:45)).

   Recommend an operation-aware persistence seam grouping mutation, generation and authorization consumption, with the interceptor emitting the intended mutation event once. Retain meaningful proof-use events separately. `IAuditSink` cannot supply transaction atomicity: its worker uses another scope/connection ([AuditGroupCommitter.cs:135](../../../../EclipsVault.Infrastructure/Persistence/AuditGroupCommitter.cs:135)). Existing sign-in verifiers also need their login-specific events separated from Profile verification.

6. **Discoverable sign-in cannot capture an account generation at begin.** Omitted or unknown usernames produce discoverable options; completion resolves ownership from the submitted credential ([PasskeyService.cs:145](../../../../EclipsVault.Infrastructure/Security/WebAuthn/PasskeyService.cs:145), [194](../../../../EclipsVault.Infrastructure/Security/WebAuthn/PasskeyService.cs:194)). Capture and fence generation when the account becomes known, before accepting its assertion; do not load today’s generation only after verification and call it original proof.

   This protects subsequent races but **does not invalidate every anonymous challenge begun before a credential change** when its passkey remains registered. That stronger pending-ceremony promise needs an explicit boundary. The proposed 120-second registration deadline and atomic consume fit the accepted policy; current client timeout and session read/remove do not implement them ([ProfileController.cs:263](../../../../EclipsVault.Web/Controllers/ProfileController.cs:263)).

7. **Generation invalidation must also reach device-list metadata.** Observations contain no generation; both registries list records by expiry without consulting account generation ([SessionModels.cs:15](../../../../EclipsVault.Core/Application/Sessions/SessionModels.cs:15), [InMemorySessionRegistry.cs:72](../../../../EclipsVault.Infrastructure/Security/Defense/InMemorySessionRegistry.cs:72), [RedisSessionRegistry.cs:104](../../../../EclipsVault.Infrastructure/Security/Defense/RedisSessionRegistry.cs:104)). Clearing records alone is insufficient: an already-running old request can record itself afterward. Preserve the observation’s original generation and filter stale/missing generations. Metadata cleanup failure must not restore authentication validity.

8. **Postcommit renewal failure must remain a committed change.** Current Profile renewal occurs after service completion and has no committed-outcome handling ([ProfileController.cs:169](../../../../EclipsVault.Web/Controllers/ProfileController.cs:169)). Existing sign-in supplies a fresh session ID, but its initial registry write is unguarded after cookie issuance ([AccountController.cs:454](../../../../EclipsVault.Web/Controllers/AccountController.cs:454)). Reusing it unchanged can turn metadata failure into a failed response.

   Recommend separating the committed mutation result from cookie/metadata delivery. Renewal failure or a lost response must never restore credentials, lower generation, retry the mutation, or retain plaintext for replay. Old sessions stay invalid; require sign-in using the committed credentials. Angular already redirects UI API 401s without replaying the request ([ui-api-errors.ts:119](../../../../EclipsVault.AngularUi/src/app/ui-api/ui-api-errors.ts:119)). Postcommit best-effort notifications fit existing behavior; email-change notification must use the captured old address rather than reload the newly active address.
