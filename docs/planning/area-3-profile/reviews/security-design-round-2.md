The proof methods and durable generation are feasible, but several details remain unresolved. This is a fresh same-model, source-only review. All nine [prior findings](security-survey.md:3) remain accounted for; accepted Q1–Q5 and [ADR-0022](../../../adr/0022-profile-security-changes-require-account-verification.md:3) specify repairs, not completed fixes. Recommendations below remain unaccepted.

1. **Fresh local proof: primitives exist; an account-verification workflow does not.**

   **Facts:** Password validation checks lockout and disabled state. TOTP and recovery verification accept a user ID independently of password verification; their existing controller supplies the earlier password/SSO stage through the MFA-pending cookie. Both require enrolled TOTP. They also write sign-in events, so calling them unchanged for Profile verification would report misleading logins. See [VaultAuthenticationService.cs:48](../../../../EclipsVault.Core/Application/Authentication/VaultAuthenticationService.cs:48), [82](../../../../EclipsVault.Core/Application/Authentication/VaultAuthenticationService.cs:82), [112](../../../../EclipsVault.Core/Application/Authentication/VaultAuthenticationService.cs:112).

   Existing passkey assertions require UV, but completion resolves the account from the submitted credential ID; it accepts no expected account ID. **Concrete hazard:** reusing this completion method for account A’s verification without comparing its result could accept account B’s valid passkey. The browser’s `allowCredentials` list does not supply server-side ownership enforcement. See [PasskeyService.cs:172](../../../../EclipsVault.Infrastructure/Security/WebAuthn/PasskeyService.cs:172).

   **Recommendation:** bind every verification to the session account on the server. Keep current-password checking for password changes if that proposed rule is accepted; UV-passkey verification alone would then be insufficient for that operation.

2. **Current OIDC cannot establish guaranteed fresh IdP proof bound to the original account.**

   **Facts:** ExternalLogin starts an ordinary challenge containing a return URL. Configuration requests neither forced reauthentication nor a maximum authentication age; `ExternalIdentityReader` does not read `auth_time`. Callback matches the returned verified email to a vault account, without comparing it to an initiating account. Issuer/subject are available for audit, but no durable issuer/subject account binding exists. See [AccountController.cs:395](../../../../EclipsVault.Web/Controllers/AccountController.cs:395), [Program.cs:188](../../../../EclipsVault.Web/Program.cs:188), [ExternalIdentityReader.cs:17](../../../../EclipsVault.Web/Authentication/ExternalIdentityReader.cs:17), [SsoSignInService.cs:46](../../../../EclipsVault.Core/Application/Sso/SsoSignInService.cs:46).

   Trusted IdP MFA can issue a full session without local TOTP enrollment. Provisioned accounts have a local password hash, but the person may not know that password or possess any local factor. See [AccountController.cs:433](../../../../EclipsVault.Web/Controllers/AccountController.cs:433), [UserAdminService.cs:109](../../../../EclipsVault.Core/Application/Users/UserAdminService.cs:109).

   **Unresolved consequence:** under the proposed local-proof-only policy, such an SSO user cannot add their first passkey or perform other protected changes. “Administrator recovery” needs a concrete path: the existing administrator interface can reset TOTP, but cannot reset an existing password or edit email. See [IUserAdminService.cs:34](../../../../EclipsVault.Core/Application/Users/IUserAdminService.cs:34). An SSO session must not silently become the fallback proof.

3. **A durable generation fits the architecture, but must accompany the original proof throughout the flow.**

   **Facts:** No generation currently exists in User, UserDto, either principal, or ceremony state. Full-cookie validation already loads the account on every request; MFA-pending cookies have six-minute absolute expiry and no corresponding account validator. See [User.cs:11](../../../../EclipsVault.Core/Domain/Entities/User.cs:11), [UserDtos.cs:6](../../../../EclipsVault.Core/Application/Authentication/UserDtos.cs:6), [VaultClaimsFactory.cs:20](../../../../EclipsVault.Web/Authentication/VaultClaimsFactory.cs:20), [Program.cs:98](../../../../EclipsVault.Web/Program.cs:98), [157](../../../../EclipsVault.Web/Program.cs:157).

   Affected issuers include local-password and SSO pending principals; TOTP, recovery, enrollment, passkey, break-glass and trusted-SSO full sign-ins; Profile cookie renewal; and secret step-up renewal. The separate [PasskeyService mapper](../../../../EclipsVault.Infrastructure/Security/WebAuthn/PasskeyService.cs:349) also needs the field.

   **Concrete hazard:** an old-password MFA-pending cookie survives a password change. If TOTP completion merely reads today’s generation and stamps it into a new cookie, the stale first-factor proof becomes valid again. The same problem occurs when an already-running mutation reloads a newer generation after verification.

   **Recommendation:** retain the generation captured when proof began; condition consumption and mutation on that expected value. Issue the replacement session using the mutation’s committed result, with a new session ID. Atomic credential changes, generation advancement and audit require a shared database commit; present repositories save separately, and standalone `IAuditSink` uses the group committer. See [ProfileService.cs:117](../../../../EclipsVault.Core/Application/Profile/ProfileService.cs:117), [155](../../../../EclipsVault.Core/Application/Profile/ProfileService.cs:155), [AuditSink.cs:54](../../../../EclipsVault.Infrastructure/Persistence/AuditSink.cs:54), [AuditSaveChangesInterceptor.cs:130](../../../../EclipsVault.Infrastructure/Persistence/Interceptors/AuditSaveChangesInterceptor.cs:130).

4. **Pending-state invalidation and rollout need explicit boundaries.**

   Cover MFA-pending sign-in/enrollment, registration challenges, account-verification assertions and issued action proofs, plus any new pending-email confirmation. Existing registration and login assertions store only challenges; registration consumption is a separate session read/remove. Discoverable passkey sign-in does not identify an account at begin, so a per-account generation cannot simply be captured there without additional design. See [ProfileController.cs:252](../../../../EclipsVault.Web/Controllers/ProfileController.cs:252), [AccountController.cs:251](../../../../EclipsVault.Web/Controllers/AccountController.cs:251), [PasskeyService.cs:145](../../../../EclipsVault.Infrastructure/Security/WebAuthn/PasskeyService.cs:145).

   **Recommendations:** reject old generation-less full/pending cookies and ceremony records at rollout; never replace a missing generation with the account’s current value. Old application nodes must also be retired before relying on the new validator. Decide whether recovery replacement, passkey removal, enrollment completion and email activation advance generation or otherwise invalidate outstanding proofs: a proof obtained using a subsequently removed credential should not remain usable accidentally.

   Session-registry records currently contain no generation, so invalid cookies can remain displayed as signed-in devices unless metadata is filtered or cleaned up. See [SessionModels.cs:15](../../../../EclipsVault.Core/Application/Sessions/SessionModels.cs:15). Keep external revocation and its partial outcomes under [ADR-0021](../../../adr/0021-removing-access-and-fail-closed-auditing.md:5); a rejected credential transaction must roll back its generation too.

5. **Email ownership verification is new functionality with no current administrator workaround.**

   **Facts:** Profile immediately replaces the active email. It is a unique login alias and the SSO matching key. There is no pending-address or mailbox-verification state. Administrator editing changes clearance/project only. See [ProfileService.cs:81](../../../../EclipsVault.Core/Application/Profile/ProfileService.cs:81), [UserConfiguration.cs:19](../../../../EclipsVault.Infrastructure/Persistence/Configurations/UserConfiguration.cs:19), [AdminController.cs:140](../../../../EclipsVault.Web/Controllers/AdminController.cs:140).

   SMTP is optional; the default is Log transport. Notification success means the sender returned, and notification failures are swallowed. Thus `Enabled` or an outbox “Sent” status cannot establish mailbox ownership. See [EmailOptions.cs:8](../../../../EclipsVault.Infrastructure/Notifications/EmailOptions.cs:8), [NotificationService.cs:127](../../../../EclipsVault.Core/Application/Notifications/NotificationService.cs:127).

   **Recommendations:** retain the old active alias until confirmation, disable self-service changes without enabled SMTP, and bind confirmation to the account/session/generation/exact target. Capture the old address for notification before activation. Decide how confirmation interacts with the proposed five-minute proof expiry. Avoid placing a redeemable verification token in the ordinary notification body log: that service persists the complete body. See [NotificationService.cs:141](../../../../EclipsVault.Core/Application/Notifications/NotificationService.cs:141).

6. **Throttling defaults are clear; the shared verifier must close existing bypasses and concurrency gaps.**

   **Facts:** IP throttling defaults to **11 unsafe Account requests per fixed 120-second window**, excluding Logout; normalized source IPs share the partition. Redis shares that budget across nodes. Account lockout defaults to **five failures for 15 minutes**. See [AuthThrottleOptions.cs:9](../../../../EclipsVault.Infrastructure/Security/Defense/AuthThrottleOptions.cs:9), [AuthThrottleFilter.cs:40](../../../../EclipsVault.Web/Authorization/AuthThrottleFilter.cs:40), [LockoutPolicy.cs:10](../../../../EclipsVault.Core/Application/Authentication/LockoutPolicy.cs:10).

   Password/TOTP/recovery login failures share lockout counting. Profile current-password checks bypass it; secret step-up and enrollment confirmation also bypass that counting. Invalid passkey assertions do not increment it. See [ProfileService.cs:95](../../../../EclipsVault.Core/Application/Profile/ProfileService.cs:95), [StepUpService.cs:26](../../../../EclipsVault.Core/Application/StepUp/StepUpService.cs:26), [VaultAuthenticationService.cs:192](../../../../EclipsVault.Core/Application/Authentication/VaultAuthenticationService.cs:192).

   **Additional concrete hazard:** two requests can validate the same TOTP step against the same old `LastTotpStep`, then both save successfully. Failure-counter increments can likewise overwrite each other. A generation advanced only on credential changes does not fix these races. See [VaultAuthenticationService.cs:98](../../../../EclipsVault.Core/Application/Authentication/VaultAuthenticationService.cs:98), [211](../../../../EclipsVault.Core/Application/Authentication/VaultAuthenticationService.cs:211), [UserRepository.cs:45](../../../../EclipsVault.Infrastructure/Persistence/Repositories/UserRepository.cs:45).

   **Recommendation:** cover new Profile proof/current-password paths and affected Legacy login, recovery, enrollment, break-glass, step-up and passkey callers through narrow shared verification mechanisms. Enforce atomic replay consumption and failure counting; reset failures after complete authentication, rather than after password success alone.
